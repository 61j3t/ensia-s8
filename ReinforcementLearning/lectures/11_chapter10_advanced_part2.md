# Chapter 10 — Advanced Topics in RL (Part 2): Model-based RL, Imitation Learning, Multi-Agent RL

## Bird's eye view

- **Three independent themes** in Part 2: (I) **Model-based RL** — agent uses a learned/known model to *plan*; (II) **Imitation Learning** — reward is unknown, only **expert demonstrations** are given; (III) **Multi-Agent RL (MARL)** — several autonomous agents share one environment.
- Model-free vs Model-based slogan: model-free **learns**, model-based **plans**. Both ultimately produce value functions / policies.
- **Models come in three flavours**: deterministic (one `s′,r` per `(s,a)`), stochastic (full distribution over `s′,r`), and **sample** (returns one drawn `s′,r`).
- **Dyna-Q** = the canonical integrated *Acting + Learning + Planning* loop: one real step + `n` simulated steps using a learned tabular model. Convergence in fewer episodes as `n` grows (5 then 50 planning steps).
- **World models** = scale Dyna-style planning to high-dim. obs: a large unsupervised **world model** (V = VAE, M = MDN-RNN) + a tiny **controller** C. Train C *inside the dream* generated by V & M, then transfer to the real env.
- **Imitation Learning (IL)** drops the reward function — only expert demos `Ξ = {ξ₁,…,ξ_D}` are available. Two roads: (1) directly learn the policy (**Behavior Cloning**, **DAgger**), (2) indirectly learn the **reward** (**Inverse RL**, **Apprenticeship Learning**).
- **Behavior Cloning** = supervised learning over expert (state, action) pairs. Brittle when policy drifts off-distribution. **DAgger** fixes this by *querying the expert on states the learner actually visits* and aggregating data.
- **Inverse RL** parameterizes reward `R(x,u) = wᵀφ(x,u)` and finds `w` such that the expert is optimal. Suffers **reward ambiguity** (`w = 0` solves it trivially).
- **Apprenticeship Learning** (Abbeel & Ng 2004) bypasses the ambiguity: just match **feature expectations** `μ(π) ≈ μ(π*)`, no need for the *true* `w*`.
- **MARL** = multiple decision-makers in a shared env. Three scenarios: **cooperative**, **competitive**, **mixed**. Formalised by normal-form games, stochastic games, POSGs. **Nash equilibrium** = no agent gains by unilateral deviation.
- **Centralized vs decentralized**: central RL over `n` agents with `|A|` actions has `|A|ⁿ` joint actions — combinatorial explosion. MARL spreads control across agents. The **CTDE** pattern (Centralized Training, Decentralized Execution) is the workhorse compromise.
- Six **MARL dimensions** to memorize: Size, Knowledge, Observability, Rewards, Objective, Centralization/Communication (+ training-execution scheme).

# I. Model-based RL

## 1. Why a model? Learning vs Planning

- **Model-free** methods rely on **learning** from real experience (the agent interacts with the env. and updates `v`/`q`/`π`).
- **Model-based** methods rely on **planning** with a model of the env. (the agent simulates experience and updates `v`/`q`/`π`).
- **Both** approaches end up computing value functions — they only differ in *where the experience comes from*.

| | **Learning** | **Planning** |
|---|---|---|
| Source of experience | real environment | a model (simulated) |
| Output | improved policy/value | improved policy/value |
| Cost per step | env. interaction (slow, costly, risky) | computation (fast, safe) |

## 2. Three types of dynamic models

| Model type | What it returns for `(s, a)` | When to use |
|---|---|---|
| **Deterministic model** | a *specific* next `s′` and `r` | predictable environments |
| **Stochastic model** | a **probability distribution** over `s′, r` | uncertain environments |
| **Sample model** | *one drawn sample* `s′, r` | exploratory rollouts, Monte-Carlo planning |

A **model** does **not** give you a policy on its own — planning is the additional step on top.

## 3. Dyna: integrated Planning, Acting, and Learning

- **Dyna** = a tabular method that interleaves:
  - **direct RL** (one real step → update `Q` via Q-learning),
  - **model learning** (one real step → update `Model(s,a)`),
  - **planning** (`n` simulated steps drawn from previously visited `(s,a)` pairs → extra `Q` updates).
- Assumes a **deterministic environment** (so `Model(s,a)` stores just `r, s′`).
- Schematic cycle: `experience → (model learning → model → planning → value/policy)` and in parallel `experience → direct RL → value/policy → acting → experience`.

### 3.1. Tabular Dyna-Q (the pseudocode on the slides)

```
Initialize Q(s, a) and Model(s, a) for all s ∈ 𝓢, a ∈ 𝒜(s)
Loop forever:
  (a) S ← current (nonterminal) state
  (b) A ← ε-greedy(S, Q)
  (c) Take action A; observe resultant reward R and next state S′
  (d) Q(S, A) ← Q(S, A) + α [R + γ maxₐ Q(S′, a) − Q(S, A)]      ← direct RL (Q-learning)
  (e) Model(S, A) ← R, S′                                       ← model learning
  (f) Loop repeat n times:                                       ← planning
        S ← random previously observed state
        A ← random action previously taken in S
        R, S′ ← Model(S, A)
        Q(S, A) ← Q(S, A) + α [R + γ maxₐ Q(S′, a) − Q(S, A)]
```

Step (d) = **direct RL** (one-step Q-learning). Step (e) = **model learning**. Step (f) = **planning** (`n` simulated `(s, a, r, s′)` reused from the model).

### 3.2. Simple-maze experiment (`S → G`)

- Steps-per-episode curve over 50 episodes for `n ∈ {0, 5, 50}` planning steps:
  - **0 planning steps** (direct RL only): hundreds of steps per episode for many episodes.
  - **5 planning steps**: converges much faster.
  - **50 planning steps**: reaches the floor of ~14 steps almost immediately.
- After **one** episode without planning, only one cell along the goal path has its policy updated. With planning (`n = 50`), an **extensive policy** has been propagated — by the end of the first episode the policy reaches *almost back to the start state*.

> Memorize: planning **amortises** each real transition into `n` Q-learning updates, so the policy spreads faster across the state space.

## 4. World Models — *can agents learn inside their own dreams?*

The "world models" line of work (Ha & Schmidhuber) is the *deep-RL* version of Dyna: replace the tabular model with neural nets that learn the env. in an unsupervised way, and let the agent train **inside its own dream**.

### 4.1. Motivation — the internal model

- Brain analogy (Jay W. Forrester quote): our internal "world" is an **abstract representation** of spatial and temporal aspects of the real world.
- Pipeline: `observation → internal model → prediction of the future → perception → fast reflexive behavior`. The agent acts on the model without re-planning every time.

### 4.2. World-model architecture: V + M + C

Most model-based RL approaches learn a model but **still train on the actual env.**. World Models split the agent into:

| Module | Role | Implementation | Size |
|---|---|---|---|
| **V** (Vision) | encode each high-dim observation into a low-dim latent `z` | **VAE** (encoder → `z` → decoder) | large (~4.3 M params in car-racing exp.) |
| **M** (Memory) | predict the future: `P(z_{t+1} \mid a_t, z_t, h_t)` | **MDN-RNN** (RNN outputting a Gaussian-mixture density) | large (~422 K params) |
| **C** (Controller) | choose actions to maximise expected cumulative reward | linear: `a_t = W_c [z_t  h_t] + b_c` | **tiny** (~867 params) |

```math
a_t = W_c \, [z_t \; h_t] + b_c
```

Three-step recipe:

1. Train a **large neural network** (V then M) to learn a world model **in an unsupervised manner**.
2. Train a **small controller** C inside this world model to solve the task.
3. **Transfer** C back into the actual environment.

### 4.3. V — the Vision model

- Input: a 2D frame of a video sequence (high-dim observation).
- A **VAE** compresses it: `frame → encoder → z → decoder → reconstructed frame`.
- V learns an **abstract, compressed** representation of the observed input.

### 4.4. M — the Memory model

- M = **Mixture Density RNN**: at each step, the RNN's hidden state `h_t` is read out by an MDN that outputs a *Gaussian mixture* over the next latent `z_{t+1}`.
- Predicts `P(z_{t+1} \mid a_t, z_t, h_t)`. Mixtures are needed because complex envs are stochastic.
- A **temperature** parameter `τ` is exposed at sampling time to control model uncertainty (low `τ` → sharp, high `τ` → noisy dreams).
- Example: **SketchRNN** (the "mosquito predictor" demo) is the same idea applied to hand-drawing.

### 4.5. C — the Controller

- C decides actions to maximise expected cumulative reward.
- Most of the agent's complexity lives in V + M; C is intentionally simple and **trained separately**.

### 4.6. V + M + C together — agent loop

```
observation → VAE (V) → z ─────────┐
                                   ├─► C ──► action ──► environment
        action ─┐                  │                       │
                ▼                  │                       │
              MDN-RNN (M) ── h ────┘                       │
                ▲────────────────────── feeds back ────────┘
```

V compresses `o_t → z_t`. M consumes `(z_t, a_t, h_{t-1})` to produce `h_t`. C maps `(z_t, h_t)` to `a_t`. Action is sent both to M (for dreaming) and to the env (real loop).

### 4.7. Practical benefits

- V and M are heavy but trained efficiently on modern **GPU** accelerators.
- C is **linear and tiny** → can be optimised by **CMA-ES** (Covariance-Matrix Adaptation Evolution Strategy), an evolutionary method that runs many rollouts on multiple CPU cores in parallel.
- Splitting model from controller lets you reuse the world model across tasks.

### 4.8. Car-Racing experiment (Gymnasium)

Procedure:
1. Collect **10 000** rollouts from a random policy.
2. Train **VAE (V)** to encode each frame to a latent `z ∈ ℝ³²`.
3. Train **MDN-RNN (M)** to model `P(z_{t+1} \mid a_t, z_t, h_t)`.
4. Evolve **Controller (C)** to maximise expected cumulative reward of a rollout.

Parameter counts: V ≈ 4 348 547 ; M ≈ 422 368 ; C ≈ 867.

Results: training curve on **CarRacing-v0** rises rapidly; the **full V + M + C** drives well, while **V + C only** (no memory) drives clearly worse — M is necessary.

### 4.9. Car-racing *dreams*

- M can simulate the future from `(z_t, h_t, a_t)`: sample `z_{t+1}` and treat it as the next observation.
- Put the trained **C** into this **dream environment** generated by M — the controller can train without touching the real env at all.
- Live demo URL on the slides: `https://worldmodels.github.io/`.

# II. Imitation Learning

## 5. Why Imitation Learning?

- Model-free and model-based RL both **assume the reward function is known**. Both collect system data to either (a) update a learned model or (b) directly update a learned value function / policy.
- **Drawbacks** of the reward-driven approach:
  - Accurate representation of the true performance objective is **challenging** (designing `R` is hard).
  - Rewards may be **sparse** → learning is expensive in data, time, memory.
- **Imitation Learning** drops that assumption: the reward function is **unknown a priori** and is **described implicitly through expert demonstrations**.

### 5.1. Where does the reward function come from?

- **Computer games** (Mnih et al. 2015): the reward is given by the game score — easy.
- **Real world** (robotics, dialog, autonomous driving): "what is the reward?" — usually no clean score, so people **use a proxy**.
- Imitation Learning instead **infers the reward function from rollouts of an expert policy**, or skips reward entirely and copies the policy.

### 5.2. Why not just clone the expert?

- Behavior cloning = "ape" the expert's motions/actions. But:
  - it does **not necessarily capture the salient parts** of the behavior;
  - the expert may have **different capabilities** than the learner;
  - and there is no understanding of the *intent*.
- So instead: **figure out what the expert is trying to achieve** (= learn the reward / the salient features).

## 6. Formal setup

Dynamics:

```math
p(x_t \mid x_{t-1}, u_{t-1})
```

An **expert demonstration** is a sequence of state-control pairs:

```math
\xi = \{(x_0, u_0), (x_1, u_1), \dots\}
```

**Definition 10.1.1 (Imitation Learning problem).** For a system with the transition model above, with states `x ∈ 𝒳` and controls `u ∈ 𝒰`, the imitation learning problem is to leverage a set of demonstrations `Ξ = {ξ₁, …, ξ_D}` from an **expert policy** `π*` to find a policy `π̂*` that imitates the expert behavior.

Two roads to solve it:

| | Approach | Method(s) |
|---|---|---|
| (1) | **Directly** learn the policy | Behavior Cloning, DAgger |
| (2) | **Indirectly**, by learning the expert's reward function | Inverse RL, Apprenticeship Learning |

## 7. Behavior Cloning (BC)

Use a set of expert demonstrations `ξ ∈ Ξ` to learn a policy `π` that imitates the expert. This is plain **supervised learning** over (state, action) pairs:

```math
\hat\pi^* \;=\; \arg\min_\pi \; \sum_{\xi \in \Xi}\; \sum_{x \in \xi}\; L\bigl(\pi(x),\, \pi^*(x)\bigr)
```

- `L` is a cost function: `p`-norms (e.g. **Euclidean**) or `f`-divergences (e.g. **KL**).
- Problems:
  - Performance is bounded by the **coverage of the expert data**.
  - Expert demonstrations are usually **not uniformly sampled** across the state space — they come from sequential trajectories.
  - Once the learner deviates, it sees **states the expert never visited** → no training signal → compounding error (**covariate shift**).

## 8. DAgger — Dataset Aggregation

- **Idea**: collect **new** expert data as needed — assume the expert can be **queried on demand**.
- When the learned policy leads to **unseen states**, just **query the expert** to label those states.

```
Algorithm 1: DAgger – Dataset Aggregation
Data:   π*
Result: π̂*
𝒟 ← ∅
Initialize π̂
for i = 1 to N do
    π_i = β_i π* + (1 − β_i) π̂
    Rollout policy π_i to sample trajectory τ = {x₀, x₁, …}
    Query expert to generate dataset 𝒟_i = {(x₀, π*(x₀)), (x₁, π*(x₁)), …}
    Aggregate datasets,  𝒟 ← 𝒟 ∪ 𝒟_i
    Retrain policy π̂ using aggregated dataset 𝒟
return π̂
```

- `β_i` is a mixing coefficient: early iterations mostly use the expert, later ones mostly the learner. `π̂` is retrained from the union of all queried `(state, expert-action)` pairs.
- DAgger fixes BC's covariate shift because it **explicitly trains on the learner's own state distribution**.

## 9. Inverse RL (IRL)

**Drawbacks of just learning policies** (BC, DAgger):
- No understanding of the **underlying reasons** for the expert's behavior — no reasoning about outcomes or intentions.
- The expert may actually be **suboptimal**.
- A policy that is optimal *for the expert* may not be optimal *for the agent* if they have different dynamics or capabilities.

**Alternative**: learn a representation of the underlying **reward function**.
- → Learn the expert's **intent**.
- → Potentially **outperform** the expert.
- → Adjust for differences in capabilities.

This is **Inverse RL**.

### 9.1. Linear reward parameterization

Inverse RL assumes a linear reward:

```math
R(x, u) \;=\; w^\top \phi(x, u)
```

- `w ∈ ℝⁿ` is the weight vector to be learned.
- `φ(x, u) : 𝒳 × 𝒰 → ℝⁿ` is a feature map.

Recall the total discounted reward under policy `π`:

```math
V^\pi_T(x) \;=\; \mathbb{E}\!\left[\sum_{t=0}^{T-1} \gamma^t \, R(x_t, \pi(x_t)) \;\middle|\; x_0 = x\right]
```

Substituting the linear reward:

```math
V^\pi_T(x) \;=\; w^\top \mu(\pi, x), \qquad
\mu(\pi, x) \;=\; \mathbb{E}_\pi\!\left[\sum_{t=0}^{T-1} \gamma^t \, \phi(x_t, \pi(x_t)) \;\middle|\; x_0 = x\right]
```

`μ(π, x)` is the **feature expectation** under policy `π` starting from `x` — typically estimated by **Monte Carlo** rollouts (e.g. directly from the expert's demonstrations for `π*`).

### 9.2. Optimality of the expert

`π*` is the expert, so:

```math
V^{\pi^*}_T(x) \;\ge\; V^{\pi}_T(x), \quad \forall x \in 𝒳,\; \forall \pi
```

Substituting the linear form:

```math
w^{*\top} \mu(\pi^*, x) \;\ge\; w^{*\top} \mu(\pi, x), \quad \forall x \in 𝒳,\; \forall \pi
```

→ **Find a vector `w` that satisfies this condition.**

**Reward ambiguity problem**: `w = 0` trivially satisfies the inequality (everything has reward 0). So the constraint *alone* does not pin down a unique reward.

## 10. Apprenticeship Learning (Abbeel & Ng 2004)

Two main ideas:

**Idea 1** — it doesn't matter how well you recover `w*`, **as long as the feature expectations match**:

```math
\| \mu(\pi, x) - \mu(\pi^*, x) \|_2 \;\le\; \varepsilon \;\;\Longrightarrow\;\; | w^\top \mu(\pi, x) - w^\top \mu(\pi^*, x) | \;\le\; \varepsilon
```

for any `w` as long as `\|w\|_2 \le 1`. (Cauchy–Schwarz.)

**Idea 2** — the initial state `x₀` is drawn from a distribution `D`:

```math
\mathbb{E}_{x_0 \sim D}[V^\pi_T(x_0)] \;=\; w^\top \mu(\pi), \qquad
\mu(\pi) \;=\; \mathbb{E}_\pi\!\left[\sum_{t=0}^{T-1} \gamma^t \, \phi(x_t, \pi(x_t))\right]
```

This averages over the initial-state distribution and removes the need to consider every `x ∈ 𝒳` when matching features.

### 10.1. Algorithm

**Objective**: find `π` that makes `μ(π)` as similar as possible to `μ(π*)`.

```
Algorithm 2: Apprenticeship Learning
Data:   μ(π*), ε
Result: π̂*
Initialize policy π₀
for i = 1 to … do
    Compute μ(π_{i−1})  (or approximate via Monte Carlo)
    Solve the max-margin problem:
        (w_i, t_i) = arg max_{w, t}  t
            s.t.  w^⊤ μ(π*) ≥ w^⊤ μ(π) + t,  ∀ π ∈ {π₀, …, π_{i−1}}
                  ‖w‖₂ ≤ 1
    if t_i ≤ ε then
        π̂* ← best feature-matching policy from {π₀, …, π_{i−1}}
        return π̂*
    Use RL to find an optimal policy π_i for reward function defined by w_i.
```

Each iteration: (1) compute the current policy's feature expectation, (2) find the `w` that **most separates** the expert from all previous policies (max-margin), (3) if the margin is small enough we are done, (4) otherwise run RL with the new reward `wᵢᵀ φ` to get the next policy.

### 10.2. Example: optimal routing across a city

The reward function is unknown. An expert shows how to drive across the city (which routes to take).

| Approach | What it does | Robustness |
|---|---|---|
| **Behavior Cloning** | Mimic the actions taken by the expert; e.g. memorize the turns at particular intersections | **Not robust** at intersections the expert never visited |
| **Apprenticeship Learning** | Identify *features* of the expert trajectories that generalise; develop a policy with the **same feature expectations** as the expert. Example features: "take routes without stop signs", "take routes with higher speed limits" | Generalises across the city — even unseen intersections inherit the right preferences |

# III. Multi-Agent RL (MARL)

## 11. Introduction

- Reference book: **MARL — Multi-Agent RL** (2024) by **Stefano V. Albrecht**, Filippos Christianos, Lukas Schäfer. `https://www.marl-book.com/`. Slides at `https://github.com/marl-book/slides`.
- Codebase in Python; Chapter 10 of the book describes how the algorithms are implemented.
- For readers already familiar with single-agent RL: read book chapter 3, then skip to chapter 9 onward.
- **Not covered**: communication in MARL is partial; evolutionary game theory is *not* covered — see Bloembergen et al. (2015).

### 11.1. What is MARL?

A MARL setting has:

- **Multiple autonomous agents** in the same env.
- **Decisions**: each agent is capable of making its **own** decisions.
- **Environment**: agents interact in a **shared** environment.

### 11.2. Goal structures

| Scenario | Goal | Example |
|---|---|---|
| **Shared goal** | All agents pursue a common objective | A fleet of mobile robots collecting and delivering goods in a warehouse; a team of drones monitoring a power plant |
| **Conflicting goals** | Each agent maximises its **own** gains | Agents trading goods in a virtual market |

### 11.3. Three MARL scenarios

| Scenario | Reward structure |
|---|---|
| **Fully cooperative** | All agents receive a shared reward (e.g. +1 to everyone whenever any agent succeeds) |
| **Competitive** | Direct competition (chess: winner +1, loser −1) — zero-sum |
| **Cooperative + competitive (mixed)** | Each agent gets a positive reward for its own successful action; once a global goal is attained, all agents are rewarded |

### 11.4. Agents in the world

A MARL system extends the single-agent loop:

- Each **agent** has goals, actions, domain knowledge.
- Agents may **communicate** with each other.
- Each agent receives its own **observations** and emits its own **actions**.
- The environment receives a **joint action** (combination of all agents' actions) and emits new observations and rewards to each agent.

```
        ┌──────────────────────────┐
Agent 1 │ goals / actions / KB ─── ┼──► action ─┐
   ▲    └──────────────────────────┘            │
   │   observation & reward                     │
        ┌──────────────────────────┐            │
Agent 2 │ goals / actions / KB ─── ┼──► action ─┤  ⊗ joint action
   ▲    └──────────────────────────┘            │     │
   │   observation & reward                     │     ▼
        ┌──────────────────────────┐            │  ┌────────────────────┐
Agent n │ goals / actions / KB ─── ┼──► action ─┘  │   Environment      │
   ▲    └──────────────────────────┘               │  (state modified   │
   │   observation & reward ◄───────────────────── │   by joint action) │
                                                   └────────────────────┘
```

### 11.5. Learning process (intuition)

The agents:
1. Try actions in their environment.
2. Collect experiences about how the env. changes from their actions.
3. Learn how the **other agents** behave.
4. Learn the skills to solve their task.
5. Learn how to **coordinate** actions with other agents.
6. May even learn to develop a **shared language** to enable communication.
7. Eventually become experts at interacting optimally to achieve their goals.

### 11.6. Formal models

| Model | Description |
|---|---|
| **Normal-form games** | Specify each player's strategy space and payoff function (one-shot) |
| **Stochastic games** | Multi-agent extension of MDPs with state transitions |
| **Partially observable stochastic games (POSGs)** | Stochastic games with partial observability |

A **solution** of a game model is a set of policies (one per agent) satisfying some desired property.

> **Nash equilibrium**: no individual agent can deviate from its policy in the solution to improve its outcome.

### 11.7. Several open MARL questions

- How to design algorithms where agents choose **optimal actions** toward their goals?
- How to design **environments** to incentivize certain long-term behaviors in agents?
- How is **information communicated and propagated** among agents?
- How do **norms, conventions, and roles** emerge in a collective of agents?

## 12. Centralized vs Decentralized decision-making

Consider **3 agents**, each with an action space of **10 actions**.

| Approach | Effective action space |
|---|---|
| **Central RL** (one policy over the joint action) | `10³ = 1000` actions |
| **MA decentralized** (3 separate RL agents) | each agent has 10 actions |

- Centralized blows up combinatorially with the number of agents.
- Decentralized scales but introduces a **coordination challenge**: agents need to coordinate their actions for the joint behaviour to be successful.
- MARL uses various approaches to **facilitate the learning of coordinated agent policies**.

Examples where decentralization is natural:
- **Autonomous driving** in an urban env. — each car needs its own local policy.
- **Search-and-rescue robots** — each agent may need to act fully independently.

## 13. The six dimensions of MARL

### 13.1. Size

- How many agents are in the environment?
- Is the number of agents **fixed**, or can it change (agents added/removed)?
- How many **states** and **actions** does the env. specify?
- Are states/actions **discrete or continuous**?
- Are actions **single values** or **multi-valued vectors**?

### 13.2. Knowledge

- Do agents know which **actions** are available to themselves *and to others*?
- Do they know their own **reward functions**, and the rewards of others?
- Do agents know the **state transition probabilities** of the env.?

### 13.3. Observability

- What can agents **observe** about their env.?
- Can agents observe the **full env. state**, or only partial/noisy observations?
- Can they observe the **actions and/or rewards** of other agents?

### 13.4. Rewards

- Are the rewards **fully cooperative**, **competitive**, or **mixed**?
- Are agents **opponents** with **zero-sum** rewards?
- Or **teammates** with **shared** rewards?
- Or do agents have to compete and cooperate in some way?

### 13.5. Objective

- Is the agents' goal to learn an **equilibrium joint policy**?
- What **type** of equilibrium (Nash, correlated, …)?
- Is performance **during** learning important, or only the **final** policies?
- Is the goal to perform well **against certain classes of other agents**?

### 13.6. Centralization / communication

- Can agents coordinate via a **central controller**?
- Or do they learn **fully independent** policies?
- Can agents **share / communicate** info during learning and/or after?
- Is the communication channel **reliable** or noisy and unreliable?

### 13.7. Training and execution algorithms

| Scheme | What it means |
|---|---|
| **Centralized training and execution** | Both stages have access to centrally shared mechanisms / info (e.g. all observations shared between agents) |
| **Decentralized training and execution** | No central info; each agent learns from **its own local** info only |
| **Centralized training with decentralized execution (CTDE)** | Best of both — assume centralization is feasible **during training** (e.g. in simulation), but policies are **executed in a fully decentralized way** |

CTDE is the standard sweet-spot pattern in modern MARL.

## 14. MARL examples

### 14.1. Multi-Robot Warehouse Management

Setting: many aisles of storage racks containing all manner of items. **Orders** specify certain items + quantities to be picked up from racks and delivered to a work station. Robots move along aisles, pick items. **Goal**: complete orders as fast and efficiently as possible.

| Aspect | Specification |
|---|---|
| **Observation** | own location, current heading within the warehouse, items currently carried, current order being serviced — *plus* info about other agents (locations, items, orders) |
| **Actions** | physical movements (rotate, accelerate, brake, pick items) + send **communication messages** to other robots (travel plans, etc.) |
| **Rewards** | individual positive reward when an agent completes an order; team reward when **any** order has been completed by **any** robot |

### 14.2. Autonomous Driving

| Aspect | Specification |
|---|---|
| **Observations** | own controlled vehicle (position on lane, orientation, speed); other nearby vehicles (info may be uncertain, noisy, or incomplete) |
| **Actions** | continuous controls (steering, accel/braking) + discrete actions (change lane, turning, overtaking) |
| **Rewards** | penalize collisions (−); positive reward for minimizing driving times; negative reward for abrupt accel/braking and for frequent lane changes |
| **Collaboration** | agents collaborate to **avoid collisions** |
| **Competition** | each car minimises **its** driving time and drives smoothly |

So autonomous driving is naturally a **mixed cooperative-competitive** MARL problem.

## Key terms (glossary)

**Model-based RL**
- **Model** — agent's representation of env. dynamics (transition + reward).
- **Deterministic / Stochastic / Sample model** — three flavours of dynamic model.
- **Dyna** — interleaved acting / direct RL / model learning / planning.
- **Dyna-Q** — tabular Q-learning Dyna with deterministic-model assumption.
- **`n`-step planning** — number of simulated `(s,a)` updates per real step in Dyna.
- **World model (V, M, C)** — large unsupervised model + tiny controller.
- **VAE** (Variational Autoencoder) — used as the **V** model.
- **MDN-RNN** (Mixture Density Network RNN) — used as the **M** model (outputs mixture-of-Gaussian over next latent).
- **Temperature `τ`** — sampling control for model uncertainty in dreams.
- **CMA-ES** — Covariance-Matrix Adaptation Evolution Strategy, used to evolve the controller's parameters.
- **Dream environment** — the env. produced by M for training C without real interaction.

**Imitation Learning**
- **Expert demonstration `ξ`** — sequence of `(x_t, u_t)` from `π*`.
- **`Ξ`** — full set of demonstrations.
- **Behavior Cloning (BC)** — supervised regression on `(state, expert action)`.
- **Covariate shift** — BC's failure mode when the learner leaves the expert's state distribution.
- **DAgger** — Dataset Aggregation; iteratively queries expert on learner-visited states.
- **Inverse RL (IRL)** — recover `R(x,u) = wᵀφ(x,u)` such that `π*` is optimal.
- **Feature map `φ`** — features of `(state, action)` used to express the reward.
- **Feature expectation `μ(π, x)`** — discounted expected feature accumulation under `π`.
- **Reward ambiguity** — `w = 0` always satisfies the optimality constraint trivially.
- **Apprenticeship Learning** — match `μ(π) ≈ μ(π*)` instead of recovering true `w*`.

**Multi-Agent RL**
- **Joint action** — concatenation of all agents' simultaneous actions.
- **Cooperative / Competitive / Mixed** — three reward-structure scenarios.
- **Normal-form game / Stochastic game / POSG** — three formal models.
- **Nash equilibrium** — no agent benefits from unilateral deviation.
- **CTDE** — Centralized Training with Decentralized Execution.
- **Coordination problem** — making decentralized agents act jointly well.
- **Six dimensions** of MARL — Size, Knowledge, Observability, Rewards, Objective, Centralization/Communication.

### Pitfalls

- **Dyna-Q assumes a deterministic environment** (`Model(s,a) ← R, S'`). Don't use it as-is on stochastic envs — you'd need a sample model and a richer update.
- **Planning ≠ thinking faster**. Each planning step is *another* Q-learning update using a *stored* `(R, S′)` from the model; it does not magically discover new transitions the model has not seen.
- **The world model is trained unsupervised first**, *before* C exists. A common confusion is thinking the whole V + M + C system is trained end-to-end — it is **not**; C is evolved separately (CMA-ES) on top of frozen V, M.
- **Dreaming is not free**: M is a Gaussian-mixture model and inherits whatever bias/limitations it has. The temperature `τ` lets you trade sharpness vs uncertainty but cannot replace missing info.
- **Behavior Cloning is not Imitation Learning** — it is a special case. The big distinction: BC needs only static data, but it has **no recovery mechanism** for out-of-distribution states.
- **DAgger requires an interactive expert**. If you only have a fixed dataset (no expert to query), DAgger is not applicable — use BC or offline-IRL approaches.
- **`R(x, u) = wᵀφ(x, u)` is a *choice* of parameterization**, not a fact. Non-linear rewards (e.g. with deep nets) are common in modern IRL but lose the clean linear-algebra structure.
- **Reward ambiguity**: in IRL, `w = 0` and many other vectors all satisfy the optimality inequality — apprenticeship learning side-steps this by matching feature expectations rather than recovering `w*`.
- **Behavior Cloning at intersections the expert never visited fails badly** — this is the canonical city-routing example: memorising turns is brittle, matching *features* (no stop signs, higher speed limits) generalises.
- **MARL ≠ multi-armed bandits** — there are state transitions and *joint* actions, which couple agents through the environment.
- **Joint-action explosion**: with `n` agents and `|A|` actions each, central RL has `|A|ⁿ` actions — intractable beyond toy problems. CTDE is the standard escape hatch.
- **Cooperative shared-reward is not always easier than competitive zero-sum** — credit-assignment among teammates can be harder than playing against an opponent with a clear scalar.
- **Nash equilibrium is a definition, not an algorithm** — finding one is in general hard (PPAD-complete for general-sum games).
- **Communication in MARL was explicitly flagged as not fully covered** by the slides — keep that in mind: not every MARL paper assumes a comm channel, and when one exists it may be **noisy / unreliable**.
