# Chapter 10 — Advanced Reinforcement Learning (Part 3): MARL (QMIX) & Hierarchical RL

## Bird's eye view

- Two advanced families covered: **Multi-Agent RL (MARL)** with focus on **QMIX**, and **Hierarchical RL (HRL)** with focus on the **Options framework** and **H-DQN**.
- **MARL setting**: cooperative **Dec-POMDP** — `n` agents act on local obs, the team gets a **single global reward**; the core challenges are **credit assignment**, **coordination**, and **non-stationarity** (other agents' policies change).
- **MARL approaches** evolved: **IQL (1993)** → no factorization, no convergence guarantee, strong empirical baseline; **VDN (2017)** → additive factorization, no monotonicity; **QMIX** → monotonic factorization via hypernetworks.
- **QMIX paradigm**: **Centralized Training with Decentralized Execution (CTDE)** — global state used to mix Q-values at training; agents execute greedily on local Q-nets at runtime.
- **Monotonicity constraint** `∂Q_tot / ∂Qₐ ≥ 0` guarantees **Individual-Global-Max (IGM)**: per-agent argmax is the joint argmax → tractable decentralized control.
- **HRL** = stack policies over **multiple levels of abstraction**: high-level picks subgoals/subtasks, low-level executes primitive actions. Mitigates the **long-horizon / sparse-reward** exploration problem.
- **Options framework** = formal generalization of actions to **temporally-extended macro-actions** `(I, π, β)` (initiation set, internal policy, termination probability), turning the problem into a **Semi-MDP**.
- **HRL pillars**: hierarchical policies, subgoal discovery, reward shaping across levels. Subtask discovery can be done jointly with policy learning or in a pre-training phase.
- **Hierarchical Q-learning** uses option-duration `τ` and discounted-target updates over option trajectories; theoretically optimal, but options blend into the MDP, limiting transfer.

# Part I — MARL: QMIX

## 1. MARL precursors

### 1.1. Independent Q-learning (IQL, Tan 1993)

- Decompose a multi-agent problem into **a collection of simultaneous single-agent problems** sharing the same environment.
- Each agent runs its own Q-learning, **ignoring** that the other agents exist (or treats them as part of the environment).
- **Drawback**: does not address the **non-stationarity** introduced by the other learning agents' changing policies.
- Like its single-agent cousin (UQ-learning), IQL has **no convergence guarantees**, even with infinite exploration.
- **In practice**: a surprisingly strong baseline in mixed and competitive games.

### 1.2. Value Decomposition Networks (VDN, Sunehag et al. 2017)

- Aim to learn a **joint action-value function** `Q_tot(τ, u)` where `τ ∈ T ≡ Tⁿ` is the joint action-observation history and `u` is the joint action.
- **Factorization**: sum of per-agent values, each conditioned only on its own history:

```math
Q_{tot}(\boldsymbol{\tau}, \mathbf{u}) = \sum_{i=1}^{n} Q_i(\tau^i, u^i; \theta^i)
```

- **No monotonicity constraint** — but the additive form is restrictive.

---

## 2. QMIX overview

### 2.1. What QMIX adds

- QMIX **factorizes** the joint action-value via a **monotonic mixing network**.
- Enables **Centralized Training with Decentralized Execution (CTDE)**: global state is exploited at training time, but at execution each agent acts on its local Q-net only.
- **Enforces a monotonicity constraint** between the joint Q and each individual utility.
- Applied e.g. to **multi-UAV coordination** and **vehicle scheduling**.

### 2.2. Architectural ingredients

- **Deep neural network** for each agent's individual Q-function.
- A **mixing network** whose **parameters are generated by state-dependent hypernetworks**.
- A **hypernetwork** = a neural network that **generates the weights/biases of another (target) network** — here, of the mixing network.
- **Why monotonicity?** It guarantees that **greedy maximization of each agent's local Q** yields the joint action that maximizes centralized `Q_tot`. This makes decentralized execution possible **without sacrificing coordinated optimization during training**.

---

## 3. QMIX problem setting

| Element | Description |
|---|---|
| Framework | Cooperative **Dec-POMDP** |
| Observation | Each agent receives a **local observation** |
| Action selection | Each agent picks actions **independently** |
| Reward | **Single global team reward** |
| Challenges | **Credit assignment** + **coordination** under partial observability |
| Training trick | **Centralized critic** can leverage the **global state** to mitigate partial observability |
| Execution constraint | Action selection at execution must use **local information only** |

---

## 4. QMIX structure

### 4.1. Components

**Local value function** (per agent `a`):
- A **deep Q-network** `Qₐ(τₐ, uₐ)` conditioned on the agent's action-observation history `τₐ` and candidate action `uₐ`.

**Mixing network**:
- Two-layer feedforward net combining all agent Q-values, parameterized by the **global state** `s`:

```math
Q_{tot}(s, \mathbf{u}) = f_{\text{mix}}\big(Q_1(\tau^1, u^1), \dots, Q_n(\tau^n, u^n);\, s\big)
```

**Monotonicity constraint**:

```math
\frac{\partial Q_{tot}}{\partial Q_a} \ge 0 \quad \forall a
```

- Enforced by forcing all **mixing-network weights** (produced by the hypernetworks) to be **non-negative**.
- Guarantees decentralized execution.

### 4.2. Per-agent network

- Each agent has an MLP → **GRU** (recurrent) → MLP head, outputting `Qₐ(τₐ, ·)`.
- The GRU hidden state `hᵃₜ` captures the action-observation history.
- The `ε`-greedy selector on top of `Qₐ` picks `uᵃₜ`.

### 4.3. Mixing network internals

- Inputs: `Q₁, …, Qₙ`.
- Layer weights `W₁, W₂` (and biases) are produced by **hypernetworks that take the global state `s` as input**.
- Mixing is monotonic because `W₁, W₂` are constrained non-negative.

---

## 5. QMIX learning

### 5.1. TD loss

Squared TD error over a target network:

```math
L(\theta) = \mathbb{E}\big[(y - Q_{tot}(s, \mathbf{u}; \theta))^2\big]
```

with target

```math
y = r + \gamma\, \max_{\mathbf{u}'} Q_{tot}^{-}(s', \mathbf{u}')
```

- `Q⁻_tot` = **periodically updated target network** (DQN-style).

### 5.2. Individual-Global-Max (IGM) guarantee

Thanks to monotonicity:

```math
\arg\max_{\mathbf{u}} Q_{tot}(s, \mathbf{u}) = \big(\arg\max_{u^1} Q_1(\tau^1, u^1), \dots, \arg\max_{u^n} Q_n(\tau^n, u^n)\big)
```

- **Decentralized greedy selection** is aligned with **joint optimality under `Q_tot`**.

---

## 6. QMIX limits

- **Cannot express arbitrary interaction terms** between agents — the monotonicity restriction is the bottleneck.
- If one agent's action ranking depends **adversarially or non-monotonically** on another agent's action, QMIX may **underfit the optimal value function even with perfect data**.
- Despite this, **monotonic mixing remains the default** for CTDE value factorization in MARL.

### 6.1. Method comparison

| Method | Year | Factorization | Monotonicity | Convergence | Comments |
|---|---|---|---|---|---|
| **IQL** | 1993 | none (independent Qs) | n/a | No guarantee | Strong empirical baseline |
| **VDN** | 2017 | **additive** `∑ Qᵢ` | not enforced | depends | Simple, restrictive |
| **QMIX** | — | **monotonic mixing** via hypernet | enforced (≥0 weights) | DQN-style | CTDE default; underfits non-monotone interactions |

# Part II — Hierarchical Reinforcement Learning (HRL)

## 7. Motivation

- HRL **extends traditional RL by incorporating a hierarchical structure** into the learning process.
- Multiple **levels of policies** at different abstraction levels; tasks are broken down into **subtasks**, each level handling a specific aspect of the overall task.
- Improves **scalability and efficiency**.
- Analogy: breaking a huge codebase into small, specific functions.
- **Why HRL helps**: when state/action spaces are **large** and the task horizon is **long**, exploration with standard RL is brittle.
- > "We think that the performance benefits of HRL are primarily due to **improved exploration using subtasks/subgoals**."

---

## 8. Four pillars of HRL

### 8.1. Hierarchical policies (level structure)

| Level | Role |
|---|---|
| **Lower-level policies** | Focus on **achieving specific goals** within the context set by higher-level policies. |
| **Higher-level policies** | **Decide which subtask or lower-level policy to activate.** |

### 8.2. Subgoal discovery

- **Subgoals = intermediate milestones** the agent must reach to accomplish the overall task.
- **Effective subgoal discovery** significantly enhances HRL performance.

### 8.3. Reward shaping

- Assign **rewards at different levels** of the hierarchy to guide learning.
- **Intermediate rewards** for hitting subgoals accelerate convergence and improve efficiency.

### 8.4. (Implicit) Policy composition

- Compose level policies so the high-level policy invokes the low-level one until termination, then re-selects.

---

## 9. Case study — H-DQN for Autonomous Robot Navigation

### 9.1. Objective

- Enable a robot to navigate a **maze-like environment** to reach a target location:
  - Avoiding obstacles.
  - Navigating efficiently.
- Decisions are needed at **two levels of abstraction**:
  - **High-level planning**.
  - **Low-level control**.

### 9.2. Two-level hierarchical model

| Controller | Responsibility |
|---|---|
| **High-Level Controller (Meta-Controller)** | Selects **subgoals** for the robot. Subgoals = intermediate states leading to the destination. Operates at an **abstract** level — overall strategy. |
| **Low-Level Controller (Subgoal Achievement)** | **Achieves the subgoals** set by the high-level controller. Fine-grained control: turning, moving forward, obstacle avoidance. Trained with a **standard DQN** approach. |

### 9.3. Implementation details

- **State representation**: sensor inputs (LiDAR, depth cameras) → distances to walls and obstacles.
- **Reward structure (hierarchical)**:
  - High-level controller is rewarded when the achieved subgoal **moves the robot closer** to the target.
  - Low-level controller is rewarded for **successful execution of movements** that contribute to achieving these subgoals.
- **Training**:
  - Simulated environment.
  - Robot learns mazes of **increasing complexity**.
  - Over time it learns **how to decompose** the navigation task into subgoals and **how to execute** them efficiently.

## 10. Options framework

### 10.1. What is an option?

- An **option `ω`** generalizes the notion of action and lets us define **macro-actions**.
- It is a form of **temporally extended action**.
- An option has **three components**:

| Component | Type | Meaning |
|---|---|---|
| **Initiation set** `I` | `I ⊆ S` (or `I : S → [0,1]` as the probability that `ω` may start in `s`) | Where the option may begin |
| **Policy** `π` | `π : S × A → [0,1]` | What the option does internally |
| **Termination condition** `β` | `β : S → [0,1]` | Probability of terminating in each state (continues with `1 − β`) |

### 10.2. Execution semantics

- If the option `ω` is taken:
  - Actions are selected according to `π`.
  - The option **terminates stochastically** according to `β`.

> Special case: if `π_ω(s) = a` and `β_ω(s) = 0` for all `s`, the option **corresponds to a primitive action that terminates in one step**.

---

## 11. Semi-MDP formulation

When using options, the problem becomes a **Semi-MDP** (decisions occur at variable time intervals).

### 11.1. Multi-step reward of an option

```math
R(s, \omega) = \mathbb{E}\big[R_1 + \gamma R_2 + \cdots + \gamma^{\tau-1} R_\tau \,\big|\, S_0 = s,\, A_{0:\tau-1} \sim \pi_\omega,\, \tau \sim \beta_\omega\big]
```

### 11.2. Dynamics model

```math
T_\gamma(s' \mid s, \omega) = \sum_{k=1}^{\infty} \gamma^k\, \Pr\big(S_k = s',\, \beta_\omega(s_k) \,\big|\, S_0 = s,\, A_{0:k-1} \sim \pi_\omega\big)
```

> Note: `T_γ` is **not** a proper conditional probability distribution because of the `γᵏ` factor, but it is **usually treated like one**.

### 11.3. Bellman equation over options

```math
V_\pi(s) = \sum_{\omega \in \Omega(s)} \pi(\omega \mid s)\, \Bigg[ R(s, \omega) + \sum_{s'} T_\gamma(s' \mid s, \omega)\, V_\pi(s') \Bigg]
```

> Once options are defined, **all the standard RL machinery applies**.

---

## 12. The HRL problem

### 12.1. Hierarchical policy structure

- Let `Ω_l` = set of options/subtasks at hierarchy level `l`.
- `Ω₁ = A` = the set of **primitive actions**.
- `Γ` denotes the **top of the hierarchy**, corresponding to the **main task**.
- The policy at level `l` is `π_l(ω_l | s)` where `ω_l ∈ Ω_l` is the chosen subtask.
- **Subtask space**: `Ω_hier = {Ω_2, Ω_3, …, Ω_Γ}`.
- **Hierarchical policy**: `π_hier = π_1 ⊙ … ⊙ π_Γ`, mapping states to primitive actions by **successively invoking the policies of descending levels**.

### 12.2. The optimization

```math
\Omega^{*}_{\text{hier}},\, \pi^{*}_{\text{hier}} = \arg\max_{\Omega_{\text{hier}}}\, \arg\max_{\pi_{\text{hier}} \mid \Omega_{\text{hier}}}\, Q^{\text{hier}}(s, a)
```

```math
Q^{\text{hier}}(s_t, a_t) = \mathbb{E}_{a \sim \pi_{\text{hier}} \mid \Omega_{\text{hier}}}\Bigg[ \sum_{i=0}^{\infty} \gamma^{t+i}\, R(s_{t+1}, a_{t+i}) \,\Big|\, s_t, a_t \Bigg]
```

### 12.3. Two subproblems

| Subproblem | Description |
|---|---|
| **Hierarchical policy learning** | Learn `π_hier` given a **fixed** hierarchy `Ω_hier`. |
| **Hierarchy learning** | Learn the **hierarchy itself** — the **subtask discovery problem**. |

> Subtask discovery can be tackled **jointly** with policy learning or as a **pre-training phase**.

---

## 13. Hierarchical Q-learning

### 13.1. Setup

- Suppose we have a set of options `O` with **fixed initiation and termination functions**.
- Suppose we have a trajectory of `(s_t, o_t, r_{t:t+τ}, s_{t+τ})` tuples, where `τ` is the **duration of the option** `o_t`.

### 13.2. Update rule (Q-learning with macro-target)

```math
y_t = \sum_{t' = t}^{\tau} \gamma^{t' - t} r_{t'} + \gamma^{\tau - t}\, Q(s_{t+\tau},\, o^{*}_{t+\tau})
```

```math
o^{*}_{t+\tau} = \arg\max_{o' \in \mathcal{O}'(s_{t+\tau})} Q(s_{t+\tau}, o')
```

with the set of **eligible options** at state `s`:

```math
\mathcal{O}'(s) = \{\, o_i : I_{o_i}(s) = 1 \,\cap\, \beta_{o_i}(s) = 0,\ \forall o_i \in \mathcal{O} \,\}
```

### 13.3. Interpretation & trade-off

- The Q-value of any option represents the **expected cumulative reward until the end of the main task**, not just until the option terminates.
- Consequence: an option is **not a standalone subtask unit** — it **blends into the core MDP**.
- **Limits transferability** of learned options across tasks.
- **But**: theoretically **guarantees optimality** of the learned hierarchical policy.

## Key terms (glossary)

- **MARL** — Multi-Agent Reinforcement Learning.
- **Dec-POMDP** — Decentralized Partially Observable MDP; cooperative, single team reward, local obs.
- **CTDE** — Centralized Training, Decentralized Execution.
- **IQL** — Independent Q-Learning (Tan 1993); each agent runs its own Q-learning.
- **VDN** — Value Decomposition Network; `Q_tot = ∑ Qᵢ`.
- **QMIX** — Monotonic mixing of per-agent Q-values via state-conditioned hypernetwork.
- **Hypernetwork** — Network whose outputs are the weights/biases of another (target) network.
- **Monotonicity constraint** — `∂Q_tot/∂Qₐ ≥ 0`; enforced via non-negative mixing weights.
- **IGM (Individual-Global-Max)** — Per-agent argmax equals joint argmax under `Q_tot`.
- **Credit assignment** — Distributing a global reward across agents/time.
- **Non-stationarity (MARL)** — Each agent's environment changes because other agents are also learning.
- **HRL** — Hierarchical RL; multiple policy levels with different abstraction.
- **Subgoal** — Intermediate milestone selected by a higher-level controller.
- **H-DQN** — Hierarchical DQN with meta-controller + low-level controller.
- **Meta-controller** — High-level policy selecting subgoals.
- **Option `(I, π, β)`** — Initiation set, internal policy, termination probability — a macro-action.
- **Semi-MDP** — MDP-like formalism where decisions are taken at variable time intervals (between options).
- **Hierarchical policy `π_hier`** — Composition `π_1 ⊙ … ⊙ π_Γ` mapping states to primitive actions.
- **Subtask discovery** — Learning the hierarchy / options themselves.

### Pitfalls

- **IQL does not address non-stationarity** — it ignores other agents' learning; no convergence guarantee.
- **VDN's additivity ≠ QMIX's monotonicity** — additive is a *special case*; both restrict the expressible `Q_tot` family.
- **The monotonicity constraint is on `Q_tot` w.r.t. each `Qₐ`**, not on a single agent's Q. It's enforced by **non-negative weights of the mixing network**, generated by the hypernet.
- **CTDE ≠ centralized control**. Centralized training uses the global state; **execution must be local-only**.
- **Hypernetwork ≠ mixing network**. The hypernet outputs the **weights** of the mixing network; only the mixing network ingests the agents' Q-values.
- **QMIX cannot represent every joint Q** — non-monotonic / adversarial interactions are out of reach even with perfect data.
- **An option is a triple `(I, π, β)`**, not just a policy — forgetting the initiation set or termination function loses the Semi-MDP semantics.
- **`T_γ(s'|s, ω)` is not a true probability distribution** because of the `γᵏ` factor — it just gets treated like one.
- **Hierarchical Q-learning uses option duration `τ`** in both the discounted reward sum and the bootstrap term `γ^{τ−t} Q(…)` — do not write a single-step Q-learning target.
- **Options bake into the MDP**: optimal under the task at hand, but **not transferable** across tasks without re-learning.
- **In H-DQN, the high-level reward is task-progress**, the low-level reward is **subgoal-execution success** — two separate signals, two separate networks.
- **HRL improves exploration via subgoals**, not by changing the underlying value function class — confusing "structured exploration" with "more expressive Q" is a common error.
